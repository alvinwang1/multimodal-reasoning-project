# How the Project Was Done So Far (Preproposal → Assignment 2 → Midterm)

A briefing that brings anyone on the team fully up to speed. For each part it covers what we did, how it was implemented (with file names), what came out, and what is still weak.
The forward-looking plan is in `plan.md`. The submitted midterm report is `report_midterm/main.tex`.

## 0. One-paragraph summary

We study **efficient multimodal reasoning**: how much image and audio input a model really needs to answer a question.
- **Setup:** we freeze **Qwen2.5-Omni-3B** and evaluate on **OmniBench** (image + audio + question, 4 options).
- **The variable:** how each item is presented to the model:
  - raw image or audio;
  - a shrunk or shortened version;
  - a text substitute (a caption or transcript);
  - or nothing at all.
- **What we measure:** accuracy, cost in input tokens, and wall-clock time.
- **Midterm baselines (one per research idea):**
  - **Idea 1:** a router that picks an input representation for each item;
  - **Idea 3:** a token-budget study;
  - **Idea 4:** text surrogates generated at test time.

  Each was evaluated on held-out items and given a failure analysis.
- **The thread through all three:** cheap inputs only work when they happen to keep the evidence the question needs, and the model gives no warning when they don't.

## 2. Dataset: OmniBench (`m-a-p/OmniBench`, Hugging Face)

**Size:** 1,142 items in a single split. We use **1,141**: one item has duplicate options and is dropped in `src/data.py::text_records`.

**Audio types:** **771 speech, 265 sound event, 105 music.**

**Fields we use:**

| Field | Meaning | Notes |
|---|---|---|
| `question`, `options` (4), `answer` | The multiple-choice question | `answer` is an option *string*; we convert it to an index |
| `image`, `audio` | Raw media | Audio decoded to 16 kHz mono |
| `image content` | Image caption | **Generated by InternVL-2-76B, not written by a person.** The report originally said "human-written"; this was fixed. |
| `audio content` | Audio text | **Human-annotated.** A transcript for speech, a description for sound and music. These descriptions often **name the answer** (the Idea 4 finding). |
| `audio type`, `task type` | Labels | 3 audio types, 8 task types |

**Data quirks we hit:**
- Item 685's audio is an MP4/M4A file with an `.mp3` name. librosa can't read it, so `src/data.py` falls back to PyAV.
- 49% of correct answers are "D".

**Music is nearly used up.** We have used 100 of the 105 music items, so a new balanced test set is impossible. This drives the cross-validation plan in `plan.md`.

## 3. The shared pipeline (used by every idea)

### 3.1 One "pass" = one forward pass of the model

Code: `src/analysis_a/{prompts,model,run}.py`, settings in `configs/default.yaml`.

1. **Build the chat prompt** (`prompts.py::build_messages`):
   - Qwen's standard system prompt.
   - The user turn contains the raw media that the configuration includes.
   - Any text substitutes go in as text, prefixed `Image description:` / `Audio transcript/description:`.
   - Then `Question: …`, `Options: A. … D. …`, and the instruction *"Answer with the option's letter from the given choices directly."*
2. **Score without generating** (`model.py::OmniScorer.score`): run one forward pass. Take the logits of the next token for the four letter tokens A–D and apply a softmax, giving a probability for each option. The prediction is the argmax. No text is generated, so this step is fast and deterministic.
3. **Option orders** (`prompts.py::permutation`):
   - Every item is asked in **3 orders**: the original plus 2 seeded shuffles, each different from the others.
   - Probabilities are mapped back to the original options (`map_back`).
   - **Accuracy = the fraction of the 3 orders answered correctly**, so it takes values in {0, ⅓, ⅔, 1}.
   - Why: the answer is "D" 49% of the time while the model prefers "B", so single-order accuracy misranks configurations.
4. **Logged per pass** (one JSON line each):
   - the item, configuration and order;
   - the probabilities and the prediction;
   - **tokens by modality** (image, audio, text, surrogate);
   - latency and peak memory (memory is approximate on MPS);
   - device and dtype.
5. **Resumable:** the runner skips passes already in the output file, so you can kill it and rerun the same command.

**Image size** is controlled by `max_pixels`. One visual token covers 28×28 pixels, and the full image is capped at 768 tokens (about 700 on average). **Audio** costs 25 tokens per second.

Code: `src/analysis_{a,b,c}/`, plus `omnibench_analysis.ipynb`. Plan: `plan_assignment2.md`.

**The subset:** 90 items, 30 per audio type, seed 42, stored in `data/subset_ids.json`.

  - The answer-position bias showed up here.

- **Analysis B (people):** a staged-reveal annotation app (`src/analysis_b/app.py`, built with Gradio).
  - Annotators first see only the question, caption and transcript, and say whether text is enough.
  - They then choose to reveal the image or the audio.
  - Each of the 4 of us annotated our share of the items.
- **Analysis C (prediction):** can cheap language signals predict which items text alone can answer?
  - Signals tried: SBERT embeddings, Empath features, and the model's confidence on caption+transcript.
  - The labels come from the model (correct under all orders) or from the people in Analysis B.
  - This is where Idea 1's router features came from.

## 6. Idea 1: Adaptive representation routing (Arjun + Lindy)

**Question:** can a cheap model pick, *for each item*, which of the 7 configurations to use, so that we get high accuracy at low cost?

**How it was built** (`src/midterm/idea1_router.py`, run with `.venv/bin/python -m src.midterm.idea1_router`):
1. **Labels.** Every one of the 300 items was run under all 7 configurations in 3 orders: **6,300 passes on the M2 Max**. The label y(i, c) is the order-averaged accuracy.
2. **Features (26 in total):**
   - **Probe (5):** run caption+transcript once (the cheapest informative pass) and take its sorted option probabilities, the gap between the top two, and the entropy.
   - **Question embedding (16):** Sentence-BERT, reduced to 16 dimensions with PCA fitted on train.
   - **Lengths (2):** caption and transcript length.
   - **Audio type (3):** one-hot.
3. **Model:**
   - One **L2-regularized logistic regression per configuration** (scikit-learn, C = 0.5, standardized features) predicts P̂(c is correct | x).
   - The labels are fractions. To train on them, each item is entered twice: once as "correct" with weight y and once as "wrong" with weight 1 − y. This is equivalent to soft-label cross-entropy.
4. **Policy:** choose `argmax_c P̂_c(x) − λ·cost_c`.
   - For the probe variants, the probe's cost is added to every choice except caption+transcript, whose answer the probe already gives.
   - λ is swept from 0 to 1.5 in 301 steps to trace an accuracy–cost curve.
   - The reported operating point is the **λ with the highest accuracy on the training set** (ties go to the cheaper option).
5. **Variants:** with or without the probe, and with or without the audio type. The audio type is unknown at deployment unless something classifies it.
6. **Baselines:**
   - each fixed configuration;
   - the **convex hull** of the fixed configurations, i.e. what you get by randomly mixing two of them;
   - **confidence cascades:** answer with caption+transcript and, if the top probability is below τ, re-ask with image+transcript or the full input (τ from 0.25 to 1.0, tuned on train);
   - the **oracle**, which picks the cheapest configuration that is best on each item.

**Results (120 test items):**
- **Fixed configurations:** full 45.3% at cost 1.00, image+transcript **54.2%** at 0.78, caption+transcript 45.0% at 0.36, question only 30.3% at 0.12.
- **Oracle:** **69.2% at cost 0.33**, which is 15 points of headroom.
- **Routers:** 44–46%, **below the hull** at their chosen λ. The only exception is up to **+5.9 points around cost 0.2** (the probe-free router).
- **Cascade:** 49.7% at 0.57. It lies on the hull: no worse than mixing, no better.
- **Feature ablation:**
  - probe + audio type alone gives **50.3%**;
  - all features give 44.2%, so the model overfits;
  - the per-item ranking quality (Spearman) is only 0.10–0.24.

**Why it fails:**
1. **Its features predict difficulty, not modality.** Entropy has a negative weight for *every* configuration, so the router learns "hard item", not "which input fixes it". It picks a best configuration on only 48% of the items that can be solved.
2. **It is overconfident.** It predicts 0.67 and is right 43% of the time, and the probe is confidently wrong, so the cascade rarely escalates.
3. **The labels are noisy.** 13% of items are never answered correctly. Many configurations tie at chance level, and 45 of the oracle's "question only" picks are luck.

**Examples:**
- **Item 1020** ("Why did the woman laugh?"): the router picks audio only and is wrong. Everything that includes the image is right.
- **Item 1047** (a ruan, which is a Chinese lute): only configurations with the human audio description get it right.

**Weaknesses to fix in the final:**
- **λ is chosen to maximize training accuracy.** That pushes toward expensive operating points and overfits on 180 items; use nested cross-validation or a cost target instead.
- **Too little training data:** 180 items.
- **A pointwise loss.** Switch to a pairwise ranking loss.
- **No features for disagreement between image and audio.**

**Figures:** `router_curve.pdf` (accuracy vs cost; dots now labeled) and `router_confusion.pdf` (router choice vs the oracle's).

## 7. Idea 3: Marginal utility of modality budgets

### 7.1 Main budget grid (Alvin; `src/idea3/{cells,run,analyze}.py`)

**Question:** how much accuracy does each extra image or audio token buy, does that depend on the audio type, and can it set a budget policy?

**How it was built:**
- **Cells** are written `v{tokens}_a{fraction}`:
  - **image** capped at 0 / 64 / 256 / 768 visual tokens (`max_pixels = 28² × tokens`);
  - **audio** keeps the **first** 0 / ¼ / ½ / all of the clip, with at least 1 second (`truncate_audio`);
  - plus 3 text cells: image+transcript, caption+audio, caption+transcript;
  - dev also gets centered-window audio cells (`a0.25c`, `a0.5c`).
- **Runs:** the 4×4 grid + 3 text cells × 3 orders, on both dev (the Assignment 2 subset) and test (Alvin's 90 items). In total **10,800 passes on a PSC V100 (fp32)**. The 64/256/768 caps average 56/240/694 tokens because of aspect-ratio rounding.
- **Score:** s = **log p(correct answer)**, averaged over the 3 orders. It is smoother than 0/1 accuracy on 90 items. Accuracy is reported too.
- **Analysis:**
  - **marginal utility** = score gain per extra token along each sweep;
  - per-item **Shapley values** for image and audio, plus their **interaction** I = s_va − s_v − s_a + s_∅ (I > 0 means they help more together);
  - **budget policies** chosen on dev and scored on test: one cell per audio type under a cost cap β, compared with one global cell, the full input, always-"D", and a per-item oracle;
  - bootstrap confidence intervals.

**Results (test):**
- **The image saturates early.** A 64-token image with full audio scores 47.0%, vs 50.0% for the full input (−3.0, 95% CI [−8.5, 2.6]), with 42% of the tokens. Going from no image to 64 tokens adds 14.8 points.
- **Cutting the audio is safe.** Keeping the first half gives about the same accuracy as the full clip.
- **Strong interaction on sound events.** The image's Shapley value is −0.74 and the interaction is **+1.28**: on its own, the image makes the model *confidently wrong*, but together with the audio it helps.
- **Per-type tables overfit.** 37.4% vs 47.0% for one global cell at β = 0.4. Cell rankings barely carry over from dev to test (Spearman 0.39–0.51).
- **Failure pattern (items 736, 726):** the image shows a static scene that fits a wrong option, and only the audio shows the action. The model takes each part of the answer from whichever modality is most salient.

### 7.2 Time-stretching ablation (Arjun + Lindy; `src/midterm/idea3_budget.py`)

**How it differs from 7.1:** this compresses the audio by **speeding it up** (same content, fewer tokens) instead of cutting it.

**Grid:**
- image keep-ratio {0, .1, .25, .5, 1} × audio keep-ratio {0, .25, .5, 1};
- run on the **120-item Idea 1/4 test set**;
- **5,760 passes on the M2 Max**.

**Results:**
- A **10% image with full audio scores 45.6%**, matching the full input (45.3%) with 37% of the image+audio tokens.
- **Speeding up audio breaks speech:** audio-only accuracy goes 37.5% → 21.7% (2×) → 12.5% (4×). Music is unaffected.
- On sound events, a 10% image raises accuracy from 26.7% to 45.8%.

**Lesson:** to save audio tokens, choose *which part* of the clip to keep. Don't speed it up.

## 8. Idea 4: Raw modalities vs generated text surrogates

### 8.1 Main run (Nikkita; `src/midterm/surrogates.py`, `src/midterm/idea4_surrogates.py`, `results/midterm/run_idea4.sh`)

**Question:** Assignment 2 found that the dataset's text matched the raw input cheaply. But that text was produced offline: the captions by a 76B model, the audio text by people. Does the advantage survive when a deployed system has to *generate* the text, and pays for generating it?

**How it was built:**
1. **Generate the surrogates** for each of the 120 test items, zero-shot with greedy decoding:
   - **Whisper large-v3-turbo** transcript (ASR);
   - **Qwen's own image caption** and **Qwen's own audio description** (the prompt asks for a verbatim transcript plus a description of any sounds or music).
   - Generation stops at `<|im_end|>` / `<|endoftext|>`, with a limit of 160 new tokens. Time and token counts are logged.
2. **Score 5 generated configurations:** generated caption + generated description, generated caption + ASR, image + generated description, image + ASR, generated caption + audio. The 7 base configurations are rerun on the **same L4** for a fair comparison. In total **4,320 passes**.
3. **Total cost** = answering cost + the cost of generating whatever the configuration needs.
4. **Analysis:**
   - paired gaps between reference and generated configurations (bootstrap with 2,000 resamples, sign-flip test with 10,000 permutations);
   - ASR output sorted into **plausible / empty / known filler phrase / repetition loop**;
   - surrogate quality as token-F1 against the human text;
   - worked examples.

**Results:**
- **Generated text loses 7.5 points** on caption+transcript (p = 0.04). With ASR the loss is 11.7, and image+ASR vs image+transcript loses 12.2 (p = 0.0002).
- **Almost all of the loss is on music (−21.7).** On speech, generated text is slightly *better* (+4.2, not significant).
- **The caption is not the problem.** Our 3B caption with audio is about as good as the 76B reference caption with audio (43.3% vs 39.7%). **The audio side is what fails.**
- **The human descriptions leak the answer.** "Ruan", "oud", "fuse burning" appear in the human text, against "guitar" and "explosion" in the generated text.
- **Cost:** about **8.9 s per item** to generate the caption and description, which is **≈25×** the 0.36 s raw route. Generating also processes *more* tokens, because the raw inputs still have to be encoded.
- **Whisper on non-speech:** 52 of 80 clips come back empty, as a filler phrase ("Thank you so much for joining us") or as a loop. Image+ASR is right 6.7% of the time on looping music clips, vs 86.7% with the human description.

### 8.2 Replication (Arjun + Lindy; `src/midterm_arjun/`, `results/midterm_arjun/`)

- The same pipeline was rerun on the M2 Max: **1,800 passes**.
- It agrees with the L4 run on 81% of predictions, with accuracies within 4 points.
- **Bug found here:** the first generation run had no end-of-turn stop. Qwen kept going, invented "Human:" turns and filled every output to the token limit. That run is kept as `generated_surrogates_v1_no_eos.json` and was reported as a failure case.
